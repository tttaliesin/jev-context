# 기억 제품 연구 적용 계획

2026-09-27. 기준 commit `e1449e8`. 근거: [유사 목적 제품 연구](agent-memory-competitive-research.md). 사용자의 “적용 계획을 문서로 만들고 그대로 진행해 줘”에 따라 이 계획을 작성하고 순서대로 실행한다.

## 목표와 이번 적용 범위

첫 적용은 연구의 P0인 **실행 서버 식별, 실제 MCP 문맥 응답 관측, 짧은 작업 복원의 확인**을 완성한다. 기존 checkpoint·예산·결정 대체 기능을 재사용한다. 앱에서 저장 상태와 마지막 복원 응답을 구분하고 최신 목표·다음 행동을 읽을 수 있게 한다. 기존 기록은 보존하고 모델 실행이나 shadow 승격을 추가하지 않는다.

P1의 자동 수집 확대·편집/가져오기와 P2의 의미 검색·자동 기억 정리는 뒤의 비교 평가 관문을 통과한 후 적용한다. 제품 전체를 한 번에 교체하거나 성능 효과가 없는 모델 호출을 추가하는 것은 연구의 권고와 맞지 않는다. 이번 완료와 후속 평가의 미실행을 결과 문서에서 별도로 표시한다.

## 실행 순서와 완료 기준

| 단계 | 변경 | 확인 방법 |
|---|---|---|
| 1 | MCP와 Desktop bridge가 시작 시 build hash·instance ID·시작 시각·계약 버전을 고정. 현재 디스크 hash와 비교 | 인스턴스 재시작 전후 ID, 실행 도중 파일 변경, hash 산출 실패 검사. Git/절대 경로 노출 없이 식별 |
| 2 | MCP transport에서 성공/부분/부족 문맥 응답의 최소 메타데이터 기록 | CLI·앱 읽기·별도 점검은 호스트 문맥 관측으로 기록하지 않음. 작업/packet/revision/근거 수/응답 바이트/시각/서버 식별만 보존 |
| 3 | Desktop에 실행 버전과 마지막 MCP 복원 응답 표시, 선택 작업의 checkpoint·다음 행동 표시 | 한국어/영어·작업/프로젝트 전환·기록 없음·오래된 코드·부족 응답. ‘현재 대화가 사용함’이라는 확정 표시 금지 |
| 4 | 복원 회귀 평가와 새 프로세스 MCP 시험 | 유효/대체된 결정, 부정 제약, 근거 revision, 삭제, 예산, 프로젝트 격리, 재시작. 모델 off로 실행 |

| 6 | 전체 Python/Node/UI 검사, Windows 패키지 생성·실제 Electron 확인, README·결과 문서·원격 반영 | 변경한 동작에 대한 검증 결과, 실패 수정, 남은 제약을 기록. 현재 호스트와 새 시험 서버를 구분 |

## 응답 관측 계약

서버는 transport가 반환할 **응답을 준비한 사실**을 기록한다. 전송 완료·호스트 수신·답변에 실제 반영은 독립적인 수신 확인 장치가 없으므로 `not_observed`다. 이름이 Codex인 클라이언트도 자체 신고 이름일 뿐 신원 검증이 아니다. 마지막 관측은 과거 기록이며 현재 연결 생존을 보장하지 않는다.

기록은 프로젝트 범위의 로컬 sidecar로 저장하며 문맥 원문·query·목표·사용자명·절대 경로·모델 입력을 포함하지 않는다. 읽기 전용에서는 기록하지 않는다. 기록 실패가 원래 MCP 응답을 실패로 바꾸지 않는다. 훼손되거나 다른 프로젝트/설정의 기록은 사용하지 않는다. 설정 hash가 바뀌었으면 이전 기록을 현재 설정의 성공으로 표시하지 않는다.

시작 시 build hash는 패키지 Python 소스와 계약 파일의 바이트 fingerprint다. Git commit이나 재현 빌드 서명을 뜻하지 않는다. 실행 중 소스 변경은 재연결 필요 상태로 표시한다. hash를 확인할 수 없는 경우 최신으로 간주하지 않는다. 기존 구버전 프로세스는 새 식별 필드를 제공할 수 없으므로 미확인으로 표시하고 강제 종료하지 않는다.

## 복원 평가와 후속 관문

이번 자동 회귀는 제품 계약 검사다. 타사 대비 사용자 효율 실험으로 소개하지 않는다. [연구 문서](agent-memory-competitive-research.md)의 30개 한국어 사례 구성을 평가 명세에 반영하고, 개발/heldout 분리·사람 검토 상태·version/hash·실패/시간초과·token 누락을 명시적으로 기록하게 한다. 실제 모델/타사 benchmark는 별도 실행 결과가 생기기 전까지 미실행이다.

P1/P2 진입 조건은 고정한 사례에서 심각한 제약 훼손·프로젝트 혼입·삭제 내용 재노출이 없어야 하며, 수동 checkpoint 대비 정확성을 떨어뜨리지 않고 사전 지정한 비용 또는 사용자 재설명을 줄이는 것이다. 기존 negative/timeout 결과는 그대로 보존한다.

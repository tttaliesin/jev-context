## 설계에서 바로잡을 해석

### 허용 판정과 실행 권한

명령의 의미를 분류하는 작업과 실제 실행 자격을 확인하는 작업은 입력과 책임이 다른 문제
예를 들어 “테스트 명령”이라는 분류만으로 프로젝트의 테스트 스크립트가 네트워크 접근이나 파일 삭제를 수행하지 않는다고 확정할 수 없는 구조
제안하는 조합은 사용자 요청 범위·호스트 권한·대상 경로·현재 상태를 먼저 확인하고, 의미 분류는 추가 검토의 필요성을 알려주는 자료로 사용
불확실한 분류의 고득점으로 금지 조건을 뒤집는 경로는 설계에서 제외

### 문맥 축소와 반대 근거

“내 주장에 맞는가”와 “판단에 필요한가”를 같은 점수로 취급하면 확인 편향 발생
관련 자료를 찾은 뒤 지지·반박·불충분을 별도로 확인하고, 관련 반대 근거를 유지하는 정책 제안
반대 근거 전체가 예산에 들어가지 않으면 존재·충돌 대상·조회 위치를 필수 목록으로 표시하고, 판단에 필요한 본문을 얻기 전 완료 판정을 보류
양쪽 모두 숨기는 방식도 누락 사실을 감추므로 완전한 해결로 간주하지 않는 기준

### 저렴한 모델로 넘기는 조건

PDF의 변수는 기존 문맥 X, 생성 출력 Y, 작업 중 추가로 읽은 입력 Z이며 같은 토큰 단위를 전제로 한 값
두 비교식의 차이를 계산하면 추가 비용은 `3X - 5Y + 3Z`
문서의 가정 안에서도 위임이 유리한 조건은 `5Y > 3X + 3Z`이며, 항상 위임이 손해라는 결론은 불성립
이 계산은 PDF에 주어진 계수를 이용한 대수적 추론이고 실제 구독 비용·가격·캐시 적중의 측정값과 구분
제안하는 설계는 작은 입력 묶음을 만들 수 있는 독립 작업에서만 위임 후보를 비교

## 현재 공식 계약과 대조

### TypeSafe

[API](https://docs.typesafe.ai/api)는 Choice·Noul·Score의 구조화된 답을 제공하며, 질문 ID만으로 모델에 질문의 의미가 전달되지 않는 계약
[Confidence](https://docs.typesafe.ai/confidence)는 Choice·Score의 분포 집중도이고 Noul에는 별도 confidence 필드가 없는 구조
실제 정답률·권한·테스트 성공과 동일시하지 않고 작업별 평가로 임계값을 선택하는 설계

[모델 문서](https://docs.typesafe.ai/models)는 텍스트 입력과 영어 중심 성능을 명시
한국어 성능, 로컬 대체 모델의 품질과 제공 방식은 별도 검증 대상으로 유지
후속 조사에서 `Laya`를 Convai Innovations의 공개 가중치 판단 모델로 확인
사용자의 `Leya` 표기는 `Laya`의 오타로 확인했으며 이전의 식별 미확인 상태를 정정

### Desktop 확장과 자동화

[MCP 문서](https://developers.openai.com/codex/mcp)는 로컬 프로세스를 통한 도구 연결을 설명하고, [스킬 문서](https://developers.openai.com/codex/skills)는 설명에서 상세 지침으로 진행하는 단계적 로딩을 설명
이 두 경로를 기본 연동 후보로 채택

[Hooks 문서](https://developers.openai.com/codex/hooks)에는 `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PreCompact`, `PostCompact` 등 이벤트가 있으며, 비관리 hook은 정의 검토와 신뢰 절차를 거치는 구조
따라서 자동 연동 자체가 불가능하다는 기존 설명은 정정 대상
문서상의 기능과 사용자 컴퓨터의 Desktop 버전·신뢰 상태에서 실제 동작하는지는 별도 확인 사항

일부 hook의 추가 문맥은 developer 문맥으로 들어가므로 임의 원문을 그대로 주입하면 자료의 권위를 잘못 높일 위험
권장안은 고정 안내와 검증된 스냅샷 ID만 hook에서 전달하고 자료 본문은 MCP 결과로 조회하는 구조
hook의 도구 관찰 범위에도 예외가 있으므로 전역 보안 경계로 가정하지 않는 기준

현재 확인한 계약에서는 PDF의 전체 프롬프트 교체·실제 KV 캐시 재구축 제어를 확립하지 못한 상태
이를 “원리상 영구 불가능”으로 단정하지 않고 해당 제어권이 검증되어야 하는 연구 항목으로 분류

## 결론의 강도

두 자료를 합쳐 모든 처리를 Jev에 맡기는 설계는 도출되지 않는 판단
채택할 공통 원리는 명시적인 상태, 좁은 판단, 필요한 자료의 점진적 제공, 코드가 관리하는 처리 경계
그 위의 데이터 구조·반대 근거 처리·Desktop 적응 계층·측정 기준은 이번 설계에서 추가한 제안
최초 프로젝트 여부, 기존 오픈소스 대비 우위, 비용 절감률은 이번 비교만으로 확정하지 않는 기준

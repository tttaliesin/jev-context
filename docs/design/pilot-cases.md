# 첫 버전 평가 사례 30개

이전 설계 참고 기록 · 제품 방향·범위·완료 기준은 [통합 설계 2.0](unified-design.md)으로 대체
아래의 현재·미구현·검증 상태는 작성 당시의 기록이며 최신 실행 상태와 구분

상세 설계 1.0 · [검증 계획](acceptance.md)을 실제 작업 형태로 구체화한 초기 사례 목록
아래 입력은 설계용 합성 예시이며 실제 사용자의 평가 자료나 실행 결과와 구분
구현 단계에서 사용자가 허용한 실제 문서·작업으로 각 유형을 대체하고 원문·기대 결과를 사람이 검토한 뒤 평가 세트 고정
같은 사례를 검색만 사용, 검색과 Laya, 검색과 OpenJev의 세 구성에 적용

## 평가 기록 양식

각 사례에 다음 값을 기록하는 설계

| 묶음 | 기록 항목 |
| --- | --- |
| 입력 | case ID, 원문 hash, 프로젝트 상태, 현재 사용자 요청, 필요한 근거 ID |
| 설정 | 검색 버전, 엔진 fingerprint, 입력 길이, 언어 프로필, 한계·예산 |
| 정답 | 사람이 검토한 기대 결과, 금지된 해석, 허용 가능한 유보 |
| 결과 | 반환 packet, 누락 근거, 오판, 유보, 범위 이탈, 사용자 수정 필요 |
| 자원 | cold·warm 구분, 전체 시간, 모델 시간, RAM·VRAM, 추가 읽기 |
| 판정 | pass·fail·not_evaluated, 근거, 재현에 필요한 revision |

번역 프로필이 없는 P23은 not_evaluated, 자료나 모델이 준비되지 않은 사례를 pass로 집계하지 않는 기준
이 사례로 질문·임계값을 조정했다면 이후 최종 평가에서는 별도 보류 사례 사용
같은 원문의 한국어·영어 변형을 다른 분할에 넣어 정답을 누출하지 않는 기준

## 초기 채택 기준

필수 범위·권한·원문 보존 규칙의 실패는 해당 기능 활성화를 보류하는 사유
모델 채택은 검색만 사용하는 구성보다 실제로 줄어든 오류·누락·확인 시간과 추가 지연을 함께 보고 결정
30개 합성 사례의 통과를 한국어 일반 성능이나 실제 사용자 작업 성공률로 발표하지 않는 기준
상세 장애 점검 T1~T38과 제품 단계별 검증은 [검증 계획](acceptance.md)에서 별도로 유지

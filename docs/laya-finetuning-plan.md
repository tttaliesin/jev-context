자체 검토: 같은 작성자의 문체/규칙 편향, 작은 시험 표본, 상황 묶음의 주관성을 명시한다. 수량 충족을 위해 이름만 바꾼 파생 문제를 분할하지 않는다. 모델 예측은 답안 작성에 사용하지 않는다. 합성 입력을 actual 프로필로 통과시키지 않는다. 자료 준비와 최종 시험 공개를 별도 단계로 보호한다. 보류44개의 원문 미확보와 대조 미완료를 구분하며 이 검토가 합성 실험을 막지는 않는다.

### 2026-09-29 승인된 후속 실행과 자체 검토

이번 실행은 남은 78개를 원문 근거로 재검토해 `agent_verified` 또는 근거가 있는 `deferred`로 정리하는 것부터 시작한다. 기존 4개와 원자료는 보존한다. 원시 대조 기록이 있는 8개, 원본 검색이 필요한 69개, 다른 실행 파일만 남은 1개 순서로 검토한다. 원본 미확보는 정답 `insufficient_evidence`로 바꾸지 않는다. 입력/원기록 hash·검토 시점·판정 이유·중요 오판 여부·근거 파일을 연결하며 사용자에게 일괄 라벨 작업을 요구하지 않는다.

자료 준비 검사를 통과해야 실제 자료 학습 경로 보완 및 기준 측정·학습·비교를 실행한다. 명시한 고정 자료의 train만 사용하고 hash 불일치/미지정 시 중단하며 공개 자료로 대체하지 않는다. SemIf 제품 기준과 미학습 Laya 기준을 구분한다. encoder 고정, head/type embedding/scorer만 학습한다(seed 20260928, batch 1, AdamW 1e-5, 100 step, CPU 4 threads, 전체 20분/step 30초, 실행 중 가용 RAM 1.5 GiB 하한). 개발 자료로 후보를 선택하고 보정 자료로만 보정한다. 후보 고정 후 시험을 공개하며 시험을 보고 수정하면 해당 시험은 소진 처리한다.

목적별 정확도·라벨별 오류·중요 오판·실행 실패·준비 시간·추론 p50/p95·프로세스 메모리와 출처 그룹 paired bootstrap 95% 구간을 보고한다. 차이 구간 하한 > 0, 중요 오판 증가 없음, p95/메모리 10% 이상 악화 없음 조건은 낮추지 않는다. 부족하거나 불확실하면 **개선 미확인**이다. 모델 하나만 실행하고 원격 CI/미승인 유료 자원을 사용하지 않으며 제품을 자동 교체하지 않는다. 개인 자료는 로컬에 보존하고 검증한 코드/기존 문서만 커밋·push한다.

자체 검토 결과: (1) 파일이 남아 있다는 사실만으로 초안을 승인하지 않고 당시 실행과 일치하는 범위만 인정한다. (2) 예측을 뺀 화면만으로 독립성이 보장되지는 않아 예약 시점과 개발 출처 충돌도 검사한다. (3) 구현자와 검토자가 같은 Codex라는 편향을 명시하며 사람 독립 평가로 표현하지 않는다. (4) 자료 미달이면 성능 비교 도구부터 늘리지 않고 검토·예약·분리 기능까지 검증한다. (5) 공개 기술 예비 학습기는 실제 학습 준비 완료로 표현하지 않는다. 기존 과거 기록의 사람 필수/CI 언급은 당시 사실이며 이번 실행 요건이 아니다.

**최신 검토 주체 변경(2026-09-29):** 사용자는 “jev가 아닌 니가 '올바른 판단' 검증하면 되지”라고 지정했다. 아래 과거 계획의 사람 검토 필수 조건은 이 변경으로 대체한다. Codex가 Jev의 예측을 정답으로 복사하지 않고 원문·실행 근거를 대조해 `agent_verified` 기준 답안을 확정할 수 있다. 사람 검토와 에이전트 검토의 출처는 별도로 기록한다. 자료 수·독립 그룹·최종 시험 분리·자동 제품 교체 금지 조건은 유지한다.

1. 현재 프로젝트의 실제 기록을 읽기 전용으로 조사한다. 600개는 수집 목표이며 없는 기록을 합성해서 실제 사례로 채우지 않는다. 입력을 복원할 수 없는 과거 판단과 모델의 예측은 학습 정답으로 쓰지 않는다. 검토 후보·출처·미확보 항목을 로컬에 남긴다.
2. 사람이 검토한 정답을 받을 데이터 계약과 그룹 단위 분리 검사를 만든다. 학습·개발·보정·최종 구분, 같은 출처·작업의 분할 간 중복, 기존 공개 평가 자료의 최종 재사용을 차단한다. 검토하지 않은 항목을 자동 승인하지 않는다.
3. 기존 공개 개발 자료로 **기술 예비 학습**을 실제 수행한다. CPU에서 encoder를 고정하고 decision head·type embedding·scorer만 100 step 학습한다. seed 20260928, batch 1, AdamW lr 1e-5, cross entropy, 4 threads. 이는 공식 전체 RLCD 학습의 재현이나 정식 품질 평가가 아니다. 처음 5 step에서 비정상 값·메모리 부족을 확인하면 중단한다. 전체 20분, step 30초, 가용 RAM 1.5 GiB 하한. 기존 가중치는 덮어쓰지 않는다.
4. 학습 전후 가중치 hash·변경된 텐서·손실·step 시간을 기록한다. 별도 경로에 저장하고 새 프로세스에서 재로드하여 선택·확률을 비교한다. 예비 실행에서 본 자료의 정답률을 개선 성능으로 보고하지 않는다.
5. 동일 구조의 Ollaya ONNX graph가 외부 safetensors를 참조하는지 확인한다. 학습 가중치를 해당 graph의 tensor offset에 맞게 패키징할 수 있으면 별도 모델 저장소·포트에서 반입한다. 모든 외부 참조와 hash를 검증하고, PyTorch와 동일 입력 12개(세 목적 각 4개)의 선택 일치·확률 최대 오차 0.005 이하를 통과해야 변환 성공으로 기록한다. 구조가 바뀐 모델에는 이 경로를 적용하지 않는다.
6. 검토한 실제 정답과 그룹 분리 자료가 확보되면 본 학습·개발 후보 선택·별도 보정·새 최종 비교를 실행한다. 미확보이면 해당 단계는 미실행으로 남긴다. GPU 비용은 CPU 예비 실행 시간으로 환산하지 않는다. 유료 원격 실행은 구체적 GPU·시간·상한이 정해진 이후 판단한다.
7. 계획 대비 결과·남은 입력·재현 방법을 문서화하고, 변경 범위에 맞는 로컬 검사·커밋·원격 반영을 수행한다. 2026-09-28 사용자 요청으로 원격 CI를 제거했으므로 완료 조건에 포함하지 않는다. 제품 실행기와 승격 설정은 사람이 검토한 최종 평가를 통과하기 전 유지한다.

## 사전 자체 검토

작성자가 구현·학습 전에 수행한 검토이며 독립 검토가 아니다.

| 문제 | 적용한 보완 |
|---|---|
| 이전 계획의 600개 실제 사례가 아직 없음 | 실제 보유량을 조사하고 미달을 명시. 합성 사례로 수량을 채우지 않음 |
| 예측을 정답으로 바꾸면 자기 오류 학습 | 모델 예측과 human expected를 다른 필드로 분리 |
| 공개된 120개는 이미 노출됨 | 예비 실행·개발 전용. 새 최종 성능 주장 금지 |
| 현재 torch는 CPU 빌드 | 실행 가능한 head 학습으로 기술 경로 먼저 검증. GPU 학습 완료로 표현하지 않음 |
| 작은 head 학습을 전체 모델 특화로 과장 가능 | 학습 파라미터 범위·목적·한계와 실제 업데이트를 기록 |

| 최종 정답 검토는 에이전트가 대행할 수 없음 | 검토 도구를 제공하고 정식 학습·평가 준비 여부를 기계적으로 검사 |

검토 완료. 위 순서로 실행한다. 본 학습의 필수 입력이 없을 때 기술 예비 실행 성공으로 전체 완료를 대신하지 않는다.

## 2026-09-28 후속: 판정 기준을 구체적인 사례로 검토

사용자에게 ‘정답’의 의미를 설명한 뒤, 세 목적별 10개씩 초안을 먼저 준비하겠다는 제안에 “진행해줘”라는 요청을 받았다. [사례와 판정 기준](laya-label-review.md)에 각 사례의 출처 종류·상황·판단 이유·오판 위험·검토 지점을 남겼다. 후속 자체 검토에서 나온 11개 보완 의견을 반영하고 단일 입력 필드를 바꾼 비교 14개를 추가해 총 44개가 됐다. 구조화 파일에서도 에이전트 제안과 확정 정답을 분리하고, 원본/비교 쌍과 같은 제작 작업을 연결한다.

이는 검토 준비 단계다. 합성 사례를 실제 기록으로 바꾸거나 사람 검토를 면제하는 변경이 아니다. 이 문서의 기준 검토, 개별 실제 학습 자료의 정답 검토, 독립 평가를 각각 구분한다. 본 학습과 모델 적용에는 위 실행 범위 6~7의 조건을 계속 적용한다.

## 2026-09-28 실제 업무 자료부터 비교 평가까지

사용자는 실제 기록 수집 → 정답 근거 검토 → 독립 분리 → 기준 성능 → 학습·비교까지 요청했다. 새 합성 자료로 부족량을 채우는 방향은 선택하지 않았다. 아래는 이번 실행 전에 보완하고 자체 검토한 계획이다.

### 실행 순서와 완료 기준

1. 현재 프로젝트 DB만 읽기 전용 트랜잭션으로 조사한다. 저장된 판단 요청, 작업 증거의 주장·명령·결과, 고정 출처를 분리한다. 실제 요청은 당시 state·질문·프로필이 보존된 경우에만 인정한다. 저장된 주장과 실행 요약을 새로 묶는 사례에는 `reconstructed_record_pair`를 표시한다. 과거 실행 보고는 에이전트 보고이며 자동으로 실측 정답이 되지 않는다. 개인 원문은 `.local/laya-finetuning/`에만 저장한다.
2. 근거 검토는 원문 보존/hash 검증, 원시 결과 파일 대조, 의미 판정 초안, 사람 확인을 구분한다. 이번에는 원시 결과가 남은 사례부터 초안과 한계를 작성한다. 원시 결과가 없거나 여러 실행이 섞인 보고는 보류한다. 일부 사례만 검토했으면 그 수와 미검토 수를 함께 보고한다. 불명확한 판정만 사람이 결정하도록 추리고, 모든 항목을 사람 검토 완료로 일괄 표시하지 않는다.
3. 원래 입력이 누락되는 원인을 기존 저장 경로에서 고친다. 새 판단의 실제 요청·결과를 기존 packet 저장소에 연결하되, 상세 입력은 일반 응답에서 제외한다. 근거가 선택에서 빠지더라도 해당 원문 참조를 packet에 연결해 삭제 정책이 계속 적용되게 한다. 도구 적합성 기록도 같은 저장소를 사용한다. 별도 수집 서비스·자동 실행·원격 전송은 만들지 않는다. 과거 입력은 소급해 채우지 않는다.
4. 준비 검사에서 설명용 44개와 공개 진단의 재사용, 구성 사례, 입력 hash 불일치, 미검토 자료를 차단한다. 작업·출처·같은 원문·원본/비교 관계를 전이적으로 묶는다. 네 분할의 모든 목적이 존재해야 하고, 최종 시험은 목적별 최소 30개를 요구한다. 600개는 기존 수집 하한이며 충분한 통계적 검증을 보장하는 숫자는 아니다. 라벨별 수와 독립 그룹 수를 함께 공개하고, 부족한 라벨은 그 라벨 성능을 확정하지 않는다. 분할과 원문 hash를 학습 전에 고정하고 최종 시험을 후보 선택에 쓰지 않는다.
5. 준비 검사가 통과한 뒤 기준 측정한다. 현재 제품의 SemIf와 추가 학습의 출발점인 미학습 Laya를 구분해 기록한다. 입력·질문 템플릿·토큰 한도·장치·스레드·모델 hash를 고정하고, 모델별로 순차 실행한다. 준비 시간과 warm 추론 p50/p95, 프로세스 트리의 관측 최대 메모리(측정 간격 포함), 목적별 정확도·혼동행렬·라벨별 오류·중요 오판·실행 실패를 남긴다. 저장된 예측만으로 새 기준 측정을 대체하지 않는다.
6. 기존 CPU 예비 실행의 자원 상한 안에서 독립 train만 사용해 별도 후보를 학습한다. development로 후보를 선택하고 calibration으로 보정한다. 최종 시험을 먼저 보고 후보를 바꾸지 않는다. frozen 시험과 같은 실행 조건에서 후보를 비교한다. 동일 사례의 성공/실패 변화 및 작업·출처 그룹 단위 paired bootstrap 95% 구간을 보고한다. 독립 그룹이 적으면 구간을 신뢰할 수 있는 개선 증거로 제시하지 않는다.
7. 개선 판정은 세 목적을 각각 확인한다. 정확도 차이의 95% 구간 하한이 0보다 크고, 중요 오판이 증가하지 않으며, p95와 메모리가 기준 대비 10% 이상 악화하지 않을 때에만 해당 목적의 개선 후보로 인정한다. 다른 목적에서 퇴보하거나 라벨·그룹 수가 부족하면 전체 개선을 선언하지 않는다. 이 수치는 이번 비교의 사전 제품 기준이며 보편적인 통계 보장은 아니다. 결과는 사람 검토된 최종 자료와 연결하며 기존 승격 조건을 우회하지 않는다. 제품 기본 모델은 자동 교체하지 않는다.

## 2026-09-29 재개: 실제 연결과 저장 검증

1. 현재 Codex 도구의 runtime instance/start/build/disk hash와 부모·자식 PID를 확인한다. 기존 연결의 재시작 성공은 같은 Codex 도구의 새 instance와 일치하는 build/disk hash로만 인정한다. 별도 SDK stdio 서버의 성공은 별도 항목으로 기록한다. 현재 호스트를 제어할 수 없으면 정확한 MCP 서버와 프로세스를 사용자에게 알리고 다른 검증을 진행한다.
2. 실제 stdio 전송으로 세 목적을 호출하고 전송 상태·질문·프로필·시점·결과를 저장 packet과 대조한다. 새 서버에서 같은 packet을 조회해 재시작 전후 동일성을 확인한다. 기존 수명 검증 스크립트를 확장하며 별도 서비스는 만들지 않는다. 검증 작업의 scope에 `data_usage:verification_only` 제약을 영구 저장하고 추출 시 학습·시험 부적격으로 표시한다. 가능하면 검증 DB를 격리한다.
3. 검증 요청과 실행 보고가 실제 업무 자료로 잘못 들어가지 않는지 확인한다. 새 감사는 기존 검토 파일을 덮어쓰지 않고 원본 ID로 대조한다. 기존 초안·개발 노출·사람 검토 상태를 잃지 않게 한다. 실제 업무 기록이 추가되지 않았다면 증가했다고 보고하지 않는다.
4. 기존 600개·목적별 시험 30개·라벨/독립 그룹·사람 정답 기준을 유지한다. 미달이면 기준 성능·본 학습·비교는 실행하지 않으며 결론은 개선 미확인이다. 대기 중에는 기록 보존·검증 제외·원시 근거 대조를 계속한다.

자체 검토: 별도 서버 검증을 현재 호스트 성공으로 오인하는 위험, 검증 요청의 학습 유입, 재추출 시 검토/노출 표시 소실을 확인했다. 각각 연결별 증거 분리, 영구 용도 표시 및 준비 검사 거절, 기존 검토 병합 시 원문 hash 일치 확인으로 보완한다. 현재 작업은 필수 문맥이 응답 최대 예산을 초과하므로 제약을 삭제하지 않고 저장 작업과 원문을 직접 읽는다. 검증은 목적이 명확한 작은 별도 내부 작업으로 수행한다. 이는 실제 업무 표본 수를 늘리기 위한 작업이 아니다.

2026-09-29 Codex 재실행 후 위 1~2단계의 남은 현재 연결 검증을 수행했다. 새 runtime과 build/disk 일치, 현재 도구가 생성한 세 목적 원요청의 DB 대조, 재실행 전 기록의 hash 보존 및 새 읽기용 서버의 복원까지 통과했다. [결과](laya-finetuning-results.md#codex-재실행-후-최종-확인)를 남겼으며, 검증용 packet은 자료 수에 합산하지 않는다. 다음 실행 조건은 실제 업무 자료와 정답 근거·독립 시험 확보이며, 재시작 요청을 반복하거나 학습 기준을 낮추지 않는다.

## Codex가 기준 답안 검토를 수행하는 절차

1. 기존 초안을 자동 승인하지 않는다. 원래 질문/후보와 원시 결과를 다시 대조한 사례부터 판정·중요 오판 여부·이유를 확정한다. 근거 부족이나 동등한 근거의 충돌은 보류한다. 데이터가 부족한 경우와 입력 자체의 정답이 `insufficient_evidence`인 경우를 구분한다.
2. `review.status=agent_verified`, 검토자 Codex, 시점, 이유, 검토한 state/원기록 hash, 확정 라벨/중요 여부, 근거 파일 경로/hash를 저장한다. Jev 출력에서 정답을 가져오지 않았음을 명시한다. `human_reviewed`로 기록하지 않는다. 학습 준비 검사는 이 근거가 갖춰진 Codex 검토와 기존 사람 검토를 구분해 허용한다.
3. 이미 개발에 노출된 자료는 Codex가 검토해도 최종 시험에 넣지 않는다. 새 최종 시험은 후보 개발에서 분리한 작업/출처로 구성하고, 고정된 판정 기준으로 예측을 보기 전에 답안을 확정한다. 같은 Codex가 답안과 구현을 검토한 데 따른 편향 가능성을 결과에 명시하며, 사람 독립 평가로 표현하지 않는다.
4. 지금은 원시 대조 가능한 첫 묶음을 확정하고 준비 검사를 다시 수행한다. 사용자는 각 사례의 라벨을 붙일 필요가 없다. 사용자 의도나 외부에만 있는 사실 없이는 판정할 수 없는 항목만 실제 사례·추천·이유와 함께 질문한다. 학습 후 제품 자동 승격은 계속 금지하며 에이전트 평가를 기존 `human_reviewed` 승격 계약으로 위장하지 않는다.

자체 검토: 평가 대상과 검토 주체가 다른데 사람만 정답을 검토하도록 강제했던 불필요한 제한을 제거했다. 반대로 외부 에이전트라는 사실만으로 정답이나 독립성이 보장되지는 않으므로, 초안과 확정 검토의 구분·원입력/판정 결합·근거 추적·시험 노출 제한을 유지한다. 새 서비스나 평가 계층은 추가하지 않는다.
## 2026-09-29 외부 조사에 따른 진단 보완

이 절은 후속 진단 실패 이후 사용자가 요청한 공식 사용법·외부 해결 사례 조사에 따른 보완이다. [출처·구현 비교·적용 한계](laya-finetuning-results.md#2026-09-29-외부-사용법학습-사례-조사)를 먼저 확인한다. 이전 1e-5 진단 실패와 A/B/C 미실행 기록은 변경하지 않는다. 아래는 다음 진단의 제안이며 이번 조사에서 실행됐다는 뜻이 아니다.

1. **공개 실패 재현과 입력 민감도:** 공식 이슈 #377의 원입력과 의미가 반대인 대조 입력을 개발용으로 표시한다. 기존 train/development에서 선택지 순서만 바꾼 입력도 마련하고, 의미 기준으로 정답 인덱스를 다시 연결한다. 새 최종 시험의 입력·예측을 사용하지 않는다. Python/Ollaya를 동일 입력·질문으로 순차 실행해 의미 판정과 원시 확률을 대조한다. 새로운 질문을 기존 고정 질문으로 덮어쓰지 않으며 최종 평가 자료로 등록하지 않는다.
2. **head 학습률 원인 분리:** 공식 head 1e-4, 공개 CPU 사례 6e-4를 근거로 동일 15개 train 진단에서 기존 1e-5와 비교할 범위를 정한다. 우선 최대 세 설정(기존 1e-5, 1e-4, 6e-4), 각 원본 시작·최대300 updates를 제안한다. 기존 CLI가 새 값을 거절하므로 제한 변경과 회귀 검사부터 명시적으로 구현해야 한다. seed/batch/자료순서/clip=1/encoder 고정/CPU4를 같게 두고 설정당 20분·step30초·가용1.5GiB·적재전4GiB 조건을 유지한다. 다른 설정을 함께 바꾸지 않는다. 정답 수뿐 아니라 같은 사례의 NLL·점수 차이·비정상 값·모듈별 갱신을 기록한다.
3. **CPU 반복 비용 개선:** 동결 encoder 특징 캐시는 공개 CPU 구현을 참고할 수 있다. 적용한다면 train만 캐시하고 모델·토크나이저·입력·질문·선택지 순서·코드 hash와 연결한다. 원래 경로와 logits·선택 일치를 먼저 검증하며 메모리 하한을 침해하면 사용하지 않는다. 진단 수를 늘리기 위해 서비스나 MoE 계층을 만들지 않는다.
4. **결과에 따른 종료 또는 다음 단계:** 일부 설정에서 정답이 증가하면 head 학습 조건이 원인에 기여했다는 제한된 근거로 기록하고 개발 평가를 거쳐 별도 후보 계획을 확정한다. 모두 실패하면 ‘고정 표현과 해당 head 조건에서 미해결’로 남기고 입력 표현·encoder 적응을 따로 조사한다. 후자는 현재 CPU 예비 실행과 비용·시간 범위가 다르므로 자동 실행하지 않는다. 진단 모델을 배포 후보로 바꾸지 않는다.

자체 검토: 기존 진단 통과 조건은 후보 탐색·최종 평가 진입을 막는 조건으로 유지한다. 그 실패가 원인 조사 자체를 끝낼 이유는 아니다. 공식 전체 학습·커뮤니티 head 학습·Ollaya 설정 편집은 서로 다른 방법이며, 출처의 성공 수치나 새 버전이 우리 환경의 개선을 보장하지 않는다. cross entropy나 clip=1을 근거 없이 결함으로 규정하지 않는다. 새 시험90개는 계속 미실행·미소진, 이전 시험은 소진 상태로 유지한다. 이번 보완은 코드·학습 설정을 변경하지 않았으며 사용자에게 추가 문제 작성이나 일괄 라벨링을 요구하지 않는다.

전체 모델 실행12시간, 한 실행90분, step30초, 적재전4GiB/실행중1.5GiB 하한, 로컬산출물40GiB를 지킨다. 주 비교9개→대조6개 순서이며 마지막2시간을 최종검증에 남긴다. 후보나 시험 결과를 보고 설정을 바꾸지 않는다.

개발450개에서 목적/라벨정확도·중요오판·NLL·seed차이·자원을 보고하고 상황묶음bootstrap10000회의95%구간을 계산한다. 최대규모 대비 모든 목적의 구간이±2%p 내이고 중요오판 증가가 없는 가장 작은 적격규모를 포화후보로 선택한다. 최대규모도 원본보다 개선되지 않으면 낮은 성능에서 정체, 구간/seed가 불확실하면 필요량미확정이다. 같은update 대조에서 차이가 사라지면 자료량만의 효과로 설명하지 않는다.

포화미확인 시 적격설정을 macro정확도→중요오판→NLL→작은규모 순으로 선택하고 해당설정의 개발정확도 중간seed를 사용한다(동률seed오름차순). 적격은 완전실행·원본대비macro정확도 비퇴보·목적별 중요오판 비증가다. 보정450개로 기존온도0.5/0.75/1/1.5/2/3을 선택한다. 반입15선택일치/확률차0.005이하와 잠금 후 SemIf→원본→후보 새시험450개×3회를 수행한다. 기존최종개선기준을 유지하고 제품자동교체하지 않는다.

자체검토 완료: 문항수와유효상황수·파생관계를 분리해 세며, 프로그램이 붙인 정답을 Codex 문장대조 완료로 대신하지 않는다. 자료준비나캐시대조가 미달하면 학습을 차단하고 해당검사 결과와 미실행 이유를 보고한다. 같은Codex 작성/검토라는 한계를 유지한다. 새서비스·원격CI·유료자원 없이 기존CLI를 확장하고 검증된공개자료/코드/문서만원격반영한다.

### 자료와 실행 경로의 자체 검토 보완

Codex가 360개 작업의 두 판정 조건을 작성하고, 결합 조건의 지지·반박·부분 확인·무관·충돌 판정 규칙과 생성 문장을 검토했다. 각 문항의 정확한 조합·hash·근거 연결은 자동 검사다. `review.scope=authored_conditions_and_rendering_rules`, `individual_manual_read=false`, `human_reviewed=false`로 범위를 명시한다. 이를 5400개 원문을 개별 수동 대조한 결과나 사람 검토로 확대하지 않는다. 문항은 서로 다른 업무 조건을 포함하지만 공통 표현 규칙을 공유한다. 자료량의 결론은 이 합성 분포에 한정하며 실제 업무에 필요한 양을 확정하지 않는다.

새 고유 입력 검사에서120개 중복이 발견돼 어떤 모델 실행 전에 수정했다. revision1과 최초 고정본은 로컬에 보존했다. 이후 revision2 실행 중 도구 후보 ID 끝번호가 정답과 연결되는 결함과 라벨별 질문 제약 차이를 발견했다. 개발 점수와 새 시험 결과를 열람하기 전에 실행을 중단하고 revision2 전체를 무효로 보존했다. 모든 라벨에 동일한 opaque 후보 ID와 동일한 질문 제약을 사용하는 revision3을 새로 고정하고 원본 모델부터 다시 시작한다. 기존 실행 시간을 포함한 12시간 시작 시각은 유지한다. 선택지 순서는 파일 hash에 더해 별도 hash로 고정한다. 실제/공개 개발 자료852개와 연결 충돌이 없음을 추가 검사했다. 의미상 파생 여부는 자동 hash 검사만으로 보장할 수 없으며 같은 작성자의 자체 검토라는 한계가 남는다.

세 seed 모두 완전 실행하고 각각 원본보다 macro정확도가 낮지 않으며 목적별 중요오판이 늘지 않은 설정만 적격으로 취급한다. 포화는 평균 그룹 구간뿐 아니라 대응 seed의 목적별 정확도 차이가±2%p 안이고 중요오판이 증가하지 않아야 인정한다. 불확실한 seed 결과를 평균으로 숨기지 않는다. 포화가 없으면 반복량 대조군도 후보 선택 범위에 포함한다. 모든 지정 순위가 같은 경우에는 더 적은 epoch를 택한다. 개발 예측은 저장할 checkpoint의 파라미터 저장 정밀도를 왕복한 상태로 계산한다. 학습 미완료나 개발 중단에도450개 행의 실패/미실행 상태를 보존한다.

revision3의 첫15개 캐시 대조를 다시 수행해 선택15/15일치·최대 확률차0을 확인했다. 무효화한 revision2의 캐시나 대조 증거를 재사용하지 않는다. revision3의 optimizer 갱신 없는 짧은 forward/backward 측정은 실효batch15당3.779초로 학습 전체 약17.57시간, 캐시 약0.83시간을 추정했다. 이는 워밍업이 포함된 추정이며 실제 실행 시간도 별도로 기록한다. 예산을 늘리거나 표본·seed·epoch 기준을 줄이지 않고 주9개를 우선 실행한다.90분/전체12시간 한도로 미완료인 실행은 성능 실패와 구분한다. 모든 비교를 끝내지 못하면 필요량 미확정을 유지한다.

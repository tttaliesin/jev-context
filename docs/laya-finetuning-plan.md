# Laya 추가 학습 실행 계획

2026-09-28. 사용자 요청: “계획대로 전부 진행해 줘”. [준비 검토](ollaya-finetuning-readiness.md)의 후속 실행이다. 기준 commit `0a3fe9a`.

## 실행 범위

1. 현재 프로젝트의 실제 기록을 읽기 전용으로 조사한다. 600개는 수집 목표이며 없는 기록을 합성해서 실제 사례로 채우지 않는다. 입력을 복원할 수 없는 과거 판단과 모델의 예측은 학습 정답으로 쓰지 않는다. 검토 후보·출처·미확보 항목을 로컬에 남긴다.
2. 사람이 검토한 정답을 받을 데이터 계약과 그룹 단위 분리 검사를 만든다. 학습·개발·보정·최종 구분, 같은 출처·작업의 분할 간 중복, 기존 공개 평가 자료의 최종 재사용을 차단한다. 검토하지 않은 항목을 자동 승인하지 않는다.
3. 기존 공개 개발 자료로 **기술 예비 학습**을 실제 수행한다. CPU에서 encoder를 고정하고 decision head·type embedding·scorer만 100 step 학습한다. seed 20260928, batch 1, AdamW lr 1e-5, cross entropy, 4 threads. 이는 공식 전체 RLCD 학습의 재현이나 정식 품질 평가가 아니다. 처음 5 step에서 비정상 값·메모리 부족을 확인하면 중단한다. 전체 20분, step 30초, 가용 RAM 1.5 GiB 하한. 기존 가중치는 덮어쓰지 않는다.
4. 학습 전후 가중치 hash·변경된 텐서·손실·step 시간을 기록한다. 별도 경로에 저장하고 새 프로세스에서 재로드하여 선택·확률을 비교한다. 예비 실행에서 본 자료의 정답률을 개선 성능으로 보고하지 않는다.
5. 동일 구조의 Ollaya ONNX graph가 외부 safetensors를 참조하는지 확인한다. 학습 가중치를 해당 graph의 tensor offset에 맞게 패키징할 수 있으면 별도 모델 저장소·포트에서 반입한다. 모든 외부 참조와 hash를 검증하고, PyTorch와 동일 입력 12개(세 목적 각 4개)의 선택 일치·확률 최대 오차 0.005 이하를 통과해야 변환 성공으로 기록한다. 구조가 바뀐 모델에는 이 경로를 적용하지 않는다.
6. 검토한 실제 정답과 그룹 분리 자료가 확보되면 본 학습·개발 후보 선택·별도 보정·새 최종 비교를 실행한다. 미확보이면 해당 단계는 미실행으로 남긴다. GPU 비용은 CPU 예비 실행 시간으로 환산하지 않는다. 유료 원격 실행은 구체적 GPU·시간·상한이 정해진 이후 판단한다.
7. 계획 대비 결과·남은 입력·재현 방법을 문서화하고, 변경 범위에 맞는 로컬 검사·커밋·원격 반영을 수행한다. 2026-09-28 사용자 요청으로 원격 CI를 제거했으므로 완료 조건에 포함하지 않는다. 제품 실행기와 승격 설정은 사람이 검토한 최종 평가를 통과하기 전 유지한다.

## 2026-09-28 후속: 판정 기준을 구체적인 사례로 검토

사용자에게 ‘정답’의 의미를 설명한 뒤, 세 목적별 10개씩 초안을 먼저 준비하겠다는 제안에 “진행해줘”라는 요청을 받았다. [사례와 판정 기준](laya-label-review.md)에 각 사례의 출처 종류·상황·판단 이유·오판 위험·검토 지점을 남겼다. 후속 자체 검토에서 나온 11개 보완 의견을 반영하고 단일 입력 필드를 바꾼 비교 14개를 추가해 총 44개가 됐다. 구조화 파일에서도 에이전트 제안과 확정 정답을 분리하고, 원본/비교 쌍과 같은 제작 작업을 연결한다.

이는 검토 준비 단계다. 합성 사례를 실제 기록으로 바꾸거나 사람 검토를 면제하는 변경이 아니다. 이 문서의 기준 검토, 개별 실제 학습 자료의 정답 검토, 독립 평가를 각각 구분한다. 본 학습과 모델 적용에는 위 실행 범위 6~7의 조건을 계속 적용한다.

## 2026-09-28 실제 업무 자료부터 비교 평가까지

사용자는 실제 기록 수집 → 정답 근거 검토 → 독립 분리 → 기준 성능 → 학습·비교까지 요청했다. 새 합성 자료로 부족량을 채우는 방향은 선택하지 않았다. 아래는 이번 실행 전에 보완하고 자체 검토한 계획이다.

### 실행 순서와 완료 기준

1. 현재 프로젝트 DB만 읽기 전용 트랜잭션으로 조사한다. 저장된 판단 요청, 작업 증거의 주장·명령·결과, 고정 출처를 분리한다. 실제 요청은 당시 state·질문·프로필이 보존된 경우에만 인정한다. 저장된 주장과 실행 요약을 새로 묶는 사례에는 `reconstructed_record_pair`를 표시한다. 과거 실행 보고는 에이전트 보고이며 자동으로 실측 정답이 되지 않는다. 개인 원문은 `.local/laya-finetuning/`에만 저장한다.
2. 근거 검토는 원문 보존/hash 검증, 원시 결과 파일 대조, 의미 판정 초안, 사람 확인을 구분한다. 이번에는 원시 결과가 남은 사례부터 초안과 한계를 작성한다. 원시 결과가 없거나 여러 실행이 섞인 보고는 보류한다. 일부 사례만 검토했으면 그 수와 미검토 수를 함께 보고한다. 불명확한 판정만 사람이 결정하도록 추리고, 모든 항목을 사람 검토 완료로 일괄 표시하지 않는다.
3. 원래 입력이 누락되는 원인을 기존 저장 경로에서 고친다. 새 판단의 실제 요청·결과를 기존 packet 저장소에 연결하되, 상세 입력은 일반 응답에서 제외한다. 근거가 선택에서 빠지더라도 해당 원문 참조를 packet에 연결해 삭제 정책이 계속 적용되게 한다. 도구 적합성 기록도 같은 저장소를 사용한다. 별도 수집 서비스·자동 실행·원격 전송은 만들지 않는다. 과거 입력은 소급해 채우지 않는다.
4. 준비 검사에서 설명용 44개와 공개 진단의 재사용, 구성 사례, 입력 hash 불일치, 미검토 자료를 차단한다. 작업·출처·같은 원문·원본/비교 관계를 전이적으로 묶는다. 네 분할의 모든 목적이 존재해야 하고, 최종 시험은 목적별 최소 30개를 요구한다. 600개는 기존 수집 하한이며 충분한 통계적 검증을 보장하는 숫자는 아니다. 라벨별 수와 독립 그룹 수를 함께 공개하고, 부족한 라벨은 그 라벨 성능을 확정하지 않는다. 분할과 원문 hash를 학습 전에 고정하고 최종 시험을 후보 선택에 쓰지 않는다.
5. 준비 검사가 통과한 뒤 기준 측정한다. 현재 제품의 SemIf와 추가 학습의 출발점인 미학습 Laya를 구분해 기록한다. 입력·질문 템플릿·토큰 한도·장치·스레드·모델 hash를 고정하고, 모델별로 순차 실행한다. 준비 시간과 warm 추론 p50/p95, 프로세스 트리의 관측 최대 메모리(측정 간격 포함), 목적별 정확도·혼동행렬·라벨별 오류·중요 오판·실행 실패를 남긴다. 저장된 예측만으로 새 기준 측정을 대체하지 않는다.
6. 기존 CPU 예비 실행의 자원 상한 안에서 독립 train만 사용해 별도 후보를 학습한다. development로 후보를 선택하고 calibration으로 보정한다. 최종 시험을 먼저 보고 후보를 바꾸지 않는다. frozen 시험과 같은 실행 조건에서 후보를 비교한다. 동일 사례의 성공/실패 변화 및 작업·출처 그룹 단위 paired bootstrap 95% 구간을 보고한다. 독립 그룹이 적으면 구간을 신뢰할 수 있는 개선 증거로 제시하지 않는다.
7. 개선 판정은 세 목적을 각각 확인한다. 정확도 차이의 95% 구간 하한이 0보다 크고, 중요 오판이 증가하지 않으며, p95와 메모리가 기준 대비 10% 이상 악화하지 않을 때에만 해당 목적의 개선 후보로 인정한다. 다른 목적에서 퇴보하거나 라벨·그룹 수가 부족하면 전체 개선을 선언하지 않는다. 이 수치는 이번 비교의 사전 제품 기준이며 보편적인 통계 보장은 아니다. 결과는 사람 검토된 최종 자료와 연결하며 기존 승격 조건을 우회하지 않는다. 제품 기본 모델은 자동 교체하지 않는다.

자체 검토 완료. 사람 정답의 독립 검토 완료를 뜻하지 않는다. 유료 자원과 원격 CI를 사용하지 않으며, 막힌 단계와 무관한 수집·검증 결함은 계속 수정한다.

## 2026-09-29 재개: 실제 연결과 저장 검증

1. 현재 Codex 도구의 runtime instance/start/build/disk hash와 부모·자식 PID를 확인한다. 기존 연결의 재시작 성공은 같은 Codex 도구의 새 instance와 일치하는 build/disk hash로만 인정한다. 별도 SDK stdio 서버의 성공은 별도 항목으로 기록한다. 현재 호스트를 제어할 수 없으면 정확한 MCP 서버와 프로세스를 사용자에게 알리고 다른 검증을 진행한다.
2. 실제 stdio 전송으로 세 목적을 호출하고 전송 상태·질문·프로필·시점·결과를 저장 packet과 대조한다. 새 서버에서 같은 packet을 조회해 재시작 전후 동일성을 확인한다. 기존 수명 검증 스크립트를 확장하며 별도 서비스는 만들지 않는다. 검증 작업의 scope에 `data_usage:verification_only` 제약을 영구 저장하고 추출 시 학습·시험 부적격으로 표시한다. 가능하면 검증 DB를 격리한다.
3. 검증 요청과 실행 보고가 실제 업무 자료로 잘못 들어가지 않는지 확인한다. 새 감사는 기존 검토 파일을 덮어쓰지 않고 원본 ID로 대조한다. 기존 초안·개발 노출·사람 검토 상태를 잃지 않게 한다. 실제 업무 기록이 추가되지 않았다면 증가했다고 보고하지 않는다.
4. 기존 600개·목적별 시험 30개·라벨/독립 그룹·사람 정답 기준을 유지한다. 미달이면 기준 성능·본 학습·비교는 실행하지 않으며 결론은 개선 미확인이다. 대기 중에는 기록 보존·검증 제외·원시 근거 대조를 계속한다.

자체 검토: 별도 서버 검증을 현재 호스트 성공으로 오인하는 위험, 검증 요청의 학습 유입, 재추출 시 검토/노출 표시 소실을 확인했다. 각각 연결별 증거 분리, 영구 용도 표시 및 준비 검사 거절, 기존 검토 병합 시 원문 hash 일치 확인으로 보완한다. 현재 작업은 필수 문맥이 응답 최대 예산을 초과하므로 제약을 삭제하지 않고 저장 작업과 원문을 직접 읽는다. 검증은 목적이 명확한 작은 별도 내부 작업으로 수행한다. 이는 실제 업무 표본 수를 늘리기 위한 작업이 아니다.

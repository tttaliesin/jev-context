# 여러 MCP 연결에서의 로컬 모델 수명

2026-09-26 사용자 요청: “반영해서 다시 설계하고 적용해줘”.

기존에는 MCP 서버마다 모델을 준비하고 서버 종료까지 보유했다. 실제로 같은 Codex 앱의 서버 네 개 중 하나가 모델을 점유하고 나머지 세 개가 20초마다 재시도했다. 작업 종료와 연결 종료가 다르다는 사실을 반영하지 못한 결함이다.

## 소유권과 시작 조건

MCP 서버는 가벼운 SharedLocalEngine 연결 객체만 만든다. 도구 목록, 상태 조회, 작업 복원, 자료 동기화, judge_mode=off는 모델을 시작하지 않는다. 실제 판단 요청만 공유 실행기의 준비를 시작한다. 처음 준비하는 동안은 빠르게 engine_preparing으로 기권하고, 준비된 뒤 다음 요청을 처리한다.

동일 실행 프로필의 요청은 독립된 로컬 실행기 하나로 모인다. 모델과 Python의 실제 경로, 프로필 및 구현 hash로 공유 범위를 구분한다. 실행기는 기존 SemIf/Laya worker 하나를 소유하며 판단을 직렬 처리한다. 준비·실패 후 무조건 반복하는 30분 재시도는 제거했다.

클라이언트의 종료는 다른 클라이언트의 모델을 종료하지 않는다. 마지막 판단 완료 이후 기본 120초 동안 실제 요청이 없고 진행 중 요청도 없으면 모델을 해제한다. 상태 조회·연결 유지 신호는 이 시간을 연장하지 않는다. 준비 시간은 유휴 시간과 분리하며 설정한 준비 제한 시간을 넘으면 unavailable로 전환한다.

## Windows 호스트 경계

Windows의 MCP SDK는 MCP 프로세스와 자식을 Job Object로 함께 종료할 수 있다. 공유 실행기는 OS가 허용한 Job 분리로 자동 기동하거나, 독립 실행 단계에서 명시적으로 시작한다. 별도 MCP client 두 개의 검증에서는 아래 persistent 실행기를 사용했다. Desktop 재시작 후 native 요청에서는 일시 실행기의 자동 기동을 관측했다. 두 방식 모두 모델은 요청 시 준비·유휴 시 해제한다.

```powershell
.venv\Scripts\python.exe -m jev_context.shared_engine --profile .local\semif-ov-profile.json --start --persistent
.venv\Scripts\python.exe -m jev_context.shared_engine --profile .local\semif-ov-profile.json --status
.venv\Scripts\python.exe -m jev_context.shared_engine --profile .local\semif-ov-profile.json --stop
```

종료 요청은 준비·판단 중이면 거절한다. 프로필이 다른 실행기를 종료하거나 잠금 파일을 삭제하지 않는다. 자동 기동은 OS가 독립 실행을 허용할 때만 수행하며, 허용되지 않으면 engine_host_required를 반환한다. MCP 수명에 종속되는 자식으로 조용히 전환하지 않는다. 자동 기동한 일시 실행기는 유휴 시 자체 종료한다. 명시적으로 설치한 persistent 실행기는 모델만 해제하고 가볍게 대기한다. OS 재시작 후 영구 서비스/예약 작업을 자동 설치하지는 않으므로 필요하면 위 시작 명령을 다시 실행한다.

실제 모델 인터프리터는 소유 실행기의 Windows Job에 들어간다. 소유 실행기가 죽으면 가상환경 launcher 아래의 실제 모델 프로세스도 종료된다. 모델 전용 Python에는 추가 패키지를 설치하지 않고 ctypes로 OS API에 연결한다.

## 요청·장애 처리

- 현재 사용자와 SYSTEM만 접근하는 전용 디렉터리에 실행기 발견 정보와 임의 인증키를 저장한다.
- 통신은 127.0.0.1에 제한한다. 상호 HMAC 인증 이후에만 원문을 보내며 pickle은 사용하지 않는다.
- JSON 프레임 크기와 연결 시간을 제한하고, 동시 접속은 8개로 제한한다. 판단 대기 시간과 통신 시간을 요청 예산에 포함한다.
- 살아 있는 실행기가 다른 프로필을 소유하면 명시적으로 거절한다. 죽은 실행기의 이전 endpoint는 OS 잠금 확인 후 복구한다.
- worker 재기동마다 응답 큐를 새로 만들어 이전 응답이 새 준비·판단에 섞이지 않게 한다.
- 준비 실패는 unavailable로 전환한다. 유휴 정리가 끝난 뒤 새 실제 요청으로 재시도할 수 있다. 상태 조회가 재시도를 일으키지는 않는다.

## 완료 기준

1. 미사용 MCP 두 개에서 worker 시작 수 0.
2. 동시 최초 요청과 준비 후 두 연결에서 실행기·worker 하나 공유.
3. 먼저 판단한 MCP를 종료해도 다른 MCP의 판단 성공 및 동일 worker 유지.
4. 상태 조회만으로는 유휴 종료가 지연되지 않으며 모델 프로세스 종료 확인.
5. 잘못된 인증·프레임, 프로세스 충돌·재시작, 죽은 endpoint에서 유한 시간 내 안전한 응답.
6. 가짜 모델 테스트와 기존 실제 모델 검증을 구분하여 기록.

모델 정확도·코딩 효율 개선은 이 수명 관리 검증으로 입증되지 않는다. shadow와 기존 평가 제한은 유지한다.

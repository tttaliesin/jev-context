# Ollaya 2차: 입력·질문 튜닝과 모델 선택 계획

2026-09-28. 기준 commit `4c884eb`. 상태: **사전 자체 검토·수정 완료, 실행 확정**. [검토 기록](ollaya-tuning-review.md).

실행 후 기록: [2차 결과](ollaya-tuning-results.md)와 [추가 학습 준비 검토](ollaya-finetuning-readiness.md). 아래 선택·중단 규칙은 최종 결과를 본 뒤 변경하지 않았다.

## 사용자가 알고 싶은 것

Ollaya는 판단 모델을 실행·관리하는 프로그램이고, 실제 정답률은 선택한 모델과 전달 방식에도 좌우된다. [1차 실험](ollaya-evaluation-results.md)은 Laya 한 종류, 질문 두 후보만 검사했다. 이번 목표는 입력 구성·질문 분해·다른 모델 선택으로 우리 한국어 작업 판단에 쓸 가능성이 커지는지 확인하는 것이다. 가중치 추가 학습은 시행하지 않고 필요성과 비용을 판정한다.

## 고정할 실험

| 항목 | 사전 규칙 |
|---|---|
| 개발 자료 | 이전 60개 전부. 이전 최종 30개도 이번에는 개발 자료로 명시 |
| 새로운 최종 진단 | 한국어 60개, 세 목적 각 20개. 정답·근거·중요 오류를 추론 전에 고정. 이전 문장 교체만 한 복제는 피하고 로그·설정·문서·권한·시점 사례 포함 |
| 공통 한계 | 모두 에이전트 작성 진단. 사람 검토 평가나 코딩 생산성 증명으로 표현하지 않음 |
| Laya 후보 | ① 기존 질문+원래 JSON ② 1차 한국어 질문+원래 JSON ③ 한국어 질문+중복을 줄인 항목별 텍스트 ④ 짧은 영어 질문+항목별 텍스트 ⑤ 중립 선택 ID(A/B/…)로 바꾼 ④ ⑥ 항목별 텍스트+예/아니오/불명 질문 분해 |
| 다른 모델 | `decider:0.8b`, 조건부 `decider:2b`. 각각 ③·④만 비교하여 조합 폭증을 제한. 영어로 안내된 모델이므로 한국어 성능을 가정하지 않음 |
| 하드웨어 조건 | CPU, 한 모델씩, 원격 GPU 없음. 0.8b는 시작 가용 RAM 6 GiB 이상, 2b는 12 GiB 이상일 때만 준비. 준비 후 가용 RAM 1.5 GiB 미만이면 해제·중단. 4b는 공식 CPU 메모리 주의와 현재 여유 메모리를 고려해 제외 |
| 질문 분해 | 관련성은 관련 여부 1문항. 근거 관계는 반박·전체지지·부분지지·무관 4문항. 도구 적합성은 위반/명시적불가·명세부족·도움됨 3문항. 상충하는 긍정이나 불명확한 결과는 근거 부족으로 합성. 오류가 하나라도 있으면 그 사례 전체 실패 |
| 실행 한도 | 각 모델 로드 300초, 각 사례 전체 15초. 분해 문항도 15초를 나누어 사용. 연속 3개 실패 시 나머지는 not_run. 시간 초과 후 기존 forward 종료·해제를 확인하기 전 다음 모델을 시작하지 않음 |
| 선택 규칙 | 모델별 개발 중요 오류 최소 → 전체 정답 최대 → 관측된 p95 최소 → 후보 ID 순. 서로 다른 목적에서 모델을 동시에 쓰는 구성은 만들지 않음 |
| 보류 설정 | 선택 후보의 최대 확률 기준 0/0.5/0.6/0.7/0.8/0.9/0.95. 개발에서 수락 20개 이상·수락 정답률 95% 이상·중요 오수락 0개인 최저 기준. 없으면 전부 보류. 분해 판단의 점수는 사용한 하위 결정의 최소 확률이며 단일 분류 확률로 해석하지 않음 |
| calibration | 이번에는 입력·모델 변경의 영향을 분리하기 위해 추가 온도 탐색은 하지 않음. 모델 기본 온도와 보류 기준을 기록. 이미 한 temperature 실험을 추가 학습으로 표현하지 않음 |
| 최종 비교 | Laya 원래 설정, 개발에서 선택한 각 모델별 설정, 현재 SemIf를 새 60개에서 한 번씩 실행. 결과를 본 뒤 후보·정답·선택 규칙 변경 금지 |
| 성공 기준 | 각 선택 모델이 SemIf 이상 정답, 중요 오류 0, 사례 전체 p95 2초 이하일 때 다음 shadow 통합 후보. 모델 전체 결론과 목적별 가능성을 구분해 보고하되 최종 결과로 새 목적 선택을 튜닝하지 않음 |

## 진행 순서

1. 계획을 자체 검토하고 별도 검토 문서에 문제·수정·실행 가능 범위를 남긴다.
2. 새 사례, 질문·변환·합성 규칙 및 테스트를 작성하고 hash로 고정한다. JSON→텍스트 변환은 관련 필드를 그대로 유지하며 정답·rationale·critical 표시는 모델에 전달하지 않는다.
3. 기존 portable Ollaya v0.7.3을 재사용한다. 프로젝트 전용 포트·모델 경로에서만 실행한다. 새 모델은 manifest와 blob 무결성을 확인하고 첫 추론 전에 lock에 기록한다.
4. 개발 실험을 완료하고 선택 파일을 저장한다. 네트워크·설치 오류는 모델 품질 오류와 구분한다. 정답률 분모에는 실행 실패·미실행을 모두 보존한다.
5. 새 최종 진단과 같은 PC의 SemIf 비교를 실행한다. 준비·지연·메모리·해제 결과를 기록하고 종료한다.
6. 일반 사용자가 이해할 수 있게 무엇을 바꿨고 왜 개선되거나 실패했는지 설명한다. 사용 가능한 설정은 재현 파일로 남긴다. 기준 미달이면 제품 실행기를 유지하고 다음 추가 학습의 데이터·시간·배포 부담을 문서화한다.
7. 한영 README 링크·결과 문서·도구 검사·원격 반영까지 완료한다. 모델 가중치와 실행 바이너리는 Git에 넣지 않는다.

## 추가 학습을 시작하는 조건

검토 보완: 최종 진단은 모든 모델의 개발 선택이 끝난 뒤에만 읽어 추론한다. 실행 실패가 있는 후보는 선택에서 제외하되 전체 개발 결과 표에 남긴다. 분해 결과에는 가짜 다중 분류 확률을 만들지 않고 별도 decision score만 보고한다. 하위 질문의 원래 답·확률과 합성 이유를 보존한다. 근거 관계에서 전체지지와 부분지지 또는 반박이 함께 긍정이면 근거 부족, 단일 긍정만 해당 관계로 매핑한다. 기능 적합성에서 금지/불가와 도움됨이 함께 긍정일 때는 명시적 제약에 따라 unfit이며, 정보 부족이 긍정이면 나머지 긍정 여부와 무관하게 insufficient_evidence로 보류한다.

추가 자원 확인은 먼저 실제 가용 RAM을 측정하고 조건 미달 모델을 다운로드 전에 제외한다. 제외 사유를 기록하며 더 작은 모델 결과로 큰 모델의 품질을 추정하지 않는다. 설치된 조건부 모델도 시작 시 조건을 다시 확인한다. 개발·최종 출력은 새 디렉터리를 사용하고 중단 기록을 덮어쓰지 않는다. 이번 작업의 활성 model PID만 종료할 수 있다. 실패로 종료되지 않는 worker가 있으면 다음 모델을 시작하지 않는다.

개발 자료와 새로운 평가 자료에서 반복되는 실패 유형이 확인되고, 입력 수정·모델 선택으로 해결되지 않으며, 목표에 맞는 모델 학습 및 Ollaya 반입 경로가 확인될 때 별도 학습 과제로 구체화한다. 현재 자체 작성 120개를 학습·검증 모두에 섞어 정답률을 올리는 방식은 사용하지 않는다. 학습 데이터 검토와 GPU 비용을 확인하지 않은 채 클라우드 학습을 실행하지 않는다.

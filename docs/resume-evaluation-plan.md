# 실제 작업 재개와 현재 로컬 판단 비교

2026-09-26 사용자 승인: UI 이후 실제 작업 재개, 세 조건 비교, 효과에 따른 적용 범위 결정의 진행.

## 과제와 목적

현재 구현에서 발견한 실제 결함을 사용한다. 등록한 요구사항 파일이 일시적으로 없어져 missing으로 관측된 뒤 복원돼도, 검색 후보와 상태 집계에서 계속 제외된다. 새 서비스에서도 기존 source ID를 지정한 검색이 정상처럼 빈 결과를 반환한다. 결함을 인위적으로 주입하지 않고 수정 전 코드를 고정한다.

목적은 저장한 목표·제약·이전 관측을 새 서비스에서 복원할 수 있는지, 그 문맥과 현재 SemIf의 판단을 제공했을 때 실제 수정 결과와 총 작업 부담이 달라지는지 확인하는 것이다. 한 결함의 개발 평가이며 일반 코딩 성능이나 사람이 검토한 미사용 평가로 해석하지 않는다.

## 실행 전에 고정하는 조건

| 조건 | 동일 코드·공개 요구사항·정책 원문 외 추가 입력 |
| --- | --- |
| E0 기본 Codex | 없음 |
| E1 저장·검색 | 새 MCP 서비스에서 복원한 작업과 모델 off 문맥 |
| E2 저장·검색＋현재 로컬 판단 | 같은 작업·원문에 현재 SemIf shadow 판단을 추가한 문맥 |

각 조건을 새 Codex 실행과 별도 디렉터리에서 세 번씩, 총 9회 실행한다. 순서는 E0/E1/E2, E1/E2/E0, E2/E0/E1로 바꾸고 한 번에 하나만 실행한다. 동일 원문을 모든 조건의 `sources/`에 제공하므로 E0도 직접 찾아 읽을 수 있다. E1/E2의 준비한 문맥은 반복 간 동일하게 유지한다. 이는 고정 문맥을 제공한 수정 비교이며 각 실행에서 MCP 호출을 다시 하는 전체 호스트 자동화 비교는 아니다.

현재 사용자 CLI 모델·추론 설정을 바꾸지 않는다. 실제로 생성한 각 세션 ID에 해당하는 실행 기록에서 모델·추론 설정·사용량을 확인한다. 평가 실행에만 hook·기억·추가 에이전트·프로젝트 MCP를 끄고 작업 디렉터리를 Git root로 구분한다. 경로와 지시·실행 기록 검토에 의한 분리이며 OS 수준의 읽기 격리를 주장하지 않는다. 승인·샌드박스 우회는 사용하지 않는다.

Codex의 JSON 이벤트와 새 실행 방식은 [공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode), 프로젝트 경계와 일회성 기능 설정은 [공식 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference) 및 설치된 CLI 도움말에서 확인했다.

## 고정 검사와 측정

- 원본 공개 검사가 통과하고 새 숨은 검사에서 실제 동작 assertion이 실패하는지 먼저 확인한다. 별도 수정 참조본의 통과도 확인한다. 실행 후 정답·검사를 바꾸지 않는다.
- 등록 파일의 누락 표시, 복원한 내용의 현재 revision 검색, 과거 revision 보존, 삭제된 원문 비복구, 미등록·비허용 원문 비수집, 읽기 전용 저장소 비변경을 검사한다.
- 허용한 제품 소스만 수정하고 테스트·입력·원문을 바꾸지 않았는지 전체 해시로 대조한다. 검사 시 복사본 모듈의 import 경로를 확인하고 Python 절대 경로를 제공한다.
- 복원·검색·모델 준비·판단·Codex 실행·외부 채점 시간을 분리한다. 실제 한 번 발생한 문맥 생성과 준비 비용은 별도 표시하고 매 시행에 반복 실측한 것처럼 합산하지 않는다. 첫 사용과 이미 준비된 문맥을 재사용한 시간 차이를 구분한다.
- 누적 입력·캐시 입력·캐시 제외 입력·출력 토큰과 관찰 가능한 도구 호출·원문 재조회 수를 기록한다. 입력 바이트를 토큰이나 금액으로 환산하지 않는다.

실행 전 동결 manifest에 코드·공개 요구사항·원문·문맥·채점·실행기·설정 hash를 기록한다. 시간 초과·실패·환경 문제도 그대로 보존한다. 공통 실행 환경에 결함이 있으면 중단해 수정하고 새 동결 자료로 다시 시작하며 기존 시행을 성공 결과에 섞지 않는다.

## 결과에 따른 판단

수정 성공과 보호 조건 충족을 먼저 본다. 3회 중앙값의 시간·캐시 제외 입력 변화는 방향을 보는 개발 신호다. 세 번 모두 성공하고 중요한 회귀가 없으면서 시간 또는 사용량에 일관된 개선이 있어야 후속 확대 평가 후보로 삼는다. 소표본의 수치 차이를 통계적 우위나 원인 확정으로 표현하지 않는다.

이번 E2는 shadow 판단 주석의 효과다. 자동 선별·축약의 효율을 검증한 것이 아니며, 사람이 검토한 별도 자료와 목적별 품질·효율 기준이 없으므로 자동 선별 승격은 하지 않는다. 발견한 실제 결함은 평가와 별도로 회귀 검증한 수정안을 제품에 반영한다.

## 2026-09-27 재실행 전 보완

`rb2`는 9회 모두 Codex 사용량 제한으로 정상 종료하지 못했다. 원본 실행과 집계는 보존하고, 오류 이벤트를 각 시행의 stdout에서 다시 확인한 별도 재집계를 `.local/resume-20260927/rb2-reanalysis.json`에 남긴다. 정상 완료 0회이며 조건 간 성능 비교는 성립하지 않는다.

새 묶음 `rb3`는 같은 수정 전 코드·요구사항·숨은 검사와 현재 로컬 프로필에서 새로 생성한 문맥을 사용한다. 이전 묶음과 성능 수치를 합치지 않는다. 집계 규칙은 새 실행 전에 다음과 같이 고정한다.

- 시도 수, 정상 종료 수, 성능 집계 대상 수, 정답 검사 통과 수, 사용량 계측 수를 구분한다.
- 정상 종료는 exit code 0, 시간 초과 없음, 완료 turn과 최종 응답 존재를 모두 요구한다. 사용량 제한 오류는 별도 상태로 남긴다.
- 비정상 종료와 허용 범위 위반은 성능 시간·토큰 중앙값에서 제외한다. 정상 종료했지만 정답 검사에 실패한 수정은 포함해 성공 사례만 고르는 편향을 막는다.
- 실패한 시도의 시간·부분 토큰은 원본 기록에 보존한다. 정상 실행이 없으면 성능 수치는 `null`이다.
- 사용량 제한이 발생한 묶음은 후속 시행을 차단한다. 실행 중 다른 비정상 종료가 발견돼도 일괄 실행을 멈추고 원인을 조사한다.
- 문맥 호출 시간과 수정 시간의 합산 추정에는 모델 준비가 포함되지 않음을 필드 이름과 설명에 표시한다. 준비 시간과 전체 문맥 생성은 별도 실측으로 보고한다.
